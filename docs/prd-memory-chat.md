# PRD — Phase 6: On-Device Memory, Chat & Buyer Profile

## 1. Overview / Problem Statement

Meridian's first five phases produce a one-shot report: address in, true 10-year cost out. But buying a home is not a one-shot decision. A buyer reads the report and immediately has follow-up questions — "What if my ceiling is $850k instead?", "Is the flood flag a dealbreaker for someone with my cash position?", "How does this compare to the place I looked at last week?". Today they have nowhere to ask.

Generic chatbots fail this buyer in two ways. They **forget context** — every session starts cold, so the buyer re-states their budget, their savings, and their risk tolerance over and over. And they **leak data to the cloud** — a buyer's income, savings, and the specific addresses they are considering are among the most sensitive financial facts they have, and a hosted LLM sends all of it off-device.

Phase 6 closes both gaps. It adds an **on-device conversational assistant with persistent, three-tier memory**, a **structured buyer profile**, and **saved reports** — and moves synthesis and chat to a **fully-local LLM**. The entire reasoning stack — Nemotron LLM, embeddings, vector memory, and relational state — runs on the DGX Spark. Nothing leaves the device.

## 2. Goals & Non-Goals

**Goals**
- Let a buyer hold a multi-turn conversation about cost of ownership that remembers what was said earlier in the session.
- Persist durable facts about the buyer (budget ceilings, cash on hand, must-avoid neighborhoods) across sessions.
- Capture a structured buyer profile and use it to personalize both chat and report synthesis.
- Let a buyer save reports and revisit them later, all on-device.
- Move all LLM inference and embedding to the local DGX Spark — remove any hosted-API dependency from the synthesis and chat paths.

**Non-Goals**
- Multi-user accounts, auth, or tenancy. The device serves a single implicit local user (profile row `id=1`).
- Letting the LLM invent financial figures. The deterministic engine still owns all numbers; the assistant reasons over them but does not fabricate dollar amounts.
- Cloud sync, sharing, or export of reports/memory off the device.
- Replacing the report flow. Chat is additive; the report remains the primary artifact.

## 3. Target User & Key Use Cases

**Primary user:** the same first-time Toronto buyer from the product brief, now mid-deliberation across multiple sessions and multiple properties.

**User stories**
- *As a buyer*, I want to set my income and budget once so I never re-type them, and every report and answer reflects my situation. *(Profile)*
- *As a buyer*, I want to ask follow-up questions about a report and have the assistant remember what we already covered. *(Short-term chat buffer)*
- *As a buyer*, I want the assistant to remember "my ceiling is $900k and I'm worried about flood risk near the Don" weeks later, without me repeating it. *(Episodic memory)*
- *As a buyer*, I want to save the reports I care about and compare them side-by-side later. *(Saved reports)*
- *As a privacy-conscious buyer*, I want certainty that my income and the addresses I'm considering never leave my device. *(On-device, non-functional)*

## 4. Functional Requirements

### (a) Conversational Assistant
- **FR-A1** — A `POST /chat` endpoint (`backend/app/api/routes/chat.py`) accepts `{session_id, message}` and returns `{reply}`. The reply is generated by the local Nemotron model via `MemoryService.chat`.
- **FR-A2** — Each turn is grounded in the buyer's profile, recalled episodic facts, and the recent conversation buffer before the model is prompted (`MemoryService.recall` assembles all three).
- **FR-A3** — When RAG is enabled and ready, the assistant injects relevant Toronto land-law context into the system prompt (`_rag().query` in the chat route → `law_context` in `MemoryService.chat`).
- **FR-A4** — Durable-fact extraction runs in the background after each user message so it never blocks the reply (`asyncio.create_task(_memory().remember(...))`).
- **FR-A5** — The assistant is constrained to reason over provided figures and must not invent specific dollar amounts (`_CHAT_SYSTEM` prompt).
- **UI** — `frontend/app/chat/page.tsx` + `frontend/components/chat-panel.tsx`: a chat surface with a per-browser `session_id` persisted in `localStorage`, optimistic user messages, a "Thinking…" state, and a clear failure message when the local model is unreachable.

### (b) Three-Tier Memory
Orchestrated by `backend/app/services/memory/memory_service.py`.
- **FR-B1 — Short-term (chat buffer):** a rolling window of recent turns per session, stored in DuckDB `chat_turns` (`AppStore.add_turn` / `recent_turns`, default last 10). Provides within- and across-session continuity for a `session_id`.
- **FR-B2 — Structured long-term:** the buyer's economic situation, read from the `user_profile` row and folded into every chat system prompt.
- **FR-B3 — Episodic long-term:** durable free-text facts (budget ceilings, cash on hand, risk tolerance, preferred/avoided neighborhoods) extracted by the local LLM (`_EXTRACT_PROMPT`) and stored as embeddings in a ChromaDB `user_memories` collection (`backend/app/services/memory/episodic_store.py`). Recall is semantic: the user message is embedded and the top-k (default 5) nearest facts are returned. Embeddings are produced by the **local** embedding server (`embedding_local_url`, :8081) — no external call.
- **FR-B4** — Memory writes degrade gracefully: if extraction returns no durable facts, or if the embedding server is unreachable, the turn proceeds without storing (logged warning, no error to the user).

### (c) Buyer Profile
- **FR-C1** — `GET /profile` and `PUT /profile` (`backend/app/api/routes/profile.py`) read and upsert a single-row profile: `name`, `email`, `phone`, `monthly_income` (`ProfileIn`/`ProfileOut` in `backend/app/schemas/profile.py`; persisted via `AppStore.upsert_profile` to the `user_profile` table keyed `id=1`).
- **FR-C2** — The profile is the structured tier of memory (FR-B2) and the personalization input for synthesis (FR-E1).
- **UI** — `frontend/app/profile/page.tsx`: a simple form with an explicit on-device privacy note, save/saved/error states, and a context refresh on save.

### (d) Saved Reports
- **FR-D1** — `POST /reports/save` persists a full report payload to DuckDB `saved_reports`, extracting `address`, `list_price`, `buyer_profile`, and `true_10_year_cost` into queryable columns while retaining the complete JSON payload (`AppStore.save_report`).
- **FR-D2** — `GET /reports` returns summaries (newest first) and `GET /reports/{id}` returns the full payload, 404 if absent.
- **UI** — `frontend/app/reports/page.tsx`: a list of saved reports showing address, buyer profile, list price, date, and true 10-year cost, with empty/loading states.

### (e) Personalized Report Synthesis
- **FR-E1** — `SynthesisService.synthesize` (`backend/app/services/synthesis/service.py`) accepts the buyer `profile` and, when present, includes a `buyer_situation` block (non-empty profile fields) in the JSON context sent to the model, so the narrative's "action" paragraph reflects the buyer's actual economic situation.
- **FR-E2** — Synthesis is **local-only**: the request goes to `nim_local_url` (:8080) with no hosted fallback. On any failure it returns `None` and the report degrades gracefully (numbers and flags still render).

## 5. Non-Functional Requirements

- **NFR-1 — On-device by construction (headline).** The complete reasoning stack runs on the DGX Spark: the Nemotron LLM (:8080), the embedding server (:8081), ChromaDB episodic memory, and DuckDB relational state all live on-device. No buyer data — income, saved addresses, chat content, or extracted facts — is sent to any external API. The synthesis path's prior hosted fallback is removed.
- **NFR-2 — Latency.** Chat replies should feel interactive; RAG land-law lookup and durable-fact extraction must not block the reply (extraction is fire-and-forget; RAG failures fall through to empty context).
- **NFR-3 — Single-user, local model.** One implicit user; no auth. The DuckDB file is shared with the data pipeline; `AppStore` is a thread-safe singleton with a single profile row.
- **NFR-4 — Graceful degradation.** Every external-to-the-process dependency (embedding server, RAG, LLM) is wrapped so failures log and fall back rather than crash a request.

## 6. NVIDIA / DGX Spark Alignment

Phase 6 is where Meridian's "runs entirely on the device" claim becomes literally true end-to-end, which maps directly onto the hackathon judging:

- **Local Nemotron (Nemotron bounty).** Both synthesis and the new conversational assistant run on the local Nemotron model on :8080 — no hosted API in either path. The same model also performs durable-fact extraction for memory.
- **NeMo Retriever embeddings.** Episodic memory is embedded by the local Nemotron RAG embedding server (:8081), the same embedding stack used for land-law RAG — semantic memory recall with zero external calls.
- **RAPIDS / GPU Monte Carlo.** The Phase-6 surfaces sit on top of the existing GPU Monte Carlo engine (CuPy, 10k trajectories) whose P10/P50/P90 outputs the assistant and synthesis reason over.
- **Unified-memory "Spark Story."** The GB10's 128 GB of unified memory holds the Nemotron LLM, the embedding model, the Monte Carlo simulation buffers, and the live memory stores (ChromaDB + DuckDB) simultaneously, with no swapping and no data leaving the box. The privacy guarantee and the performance story are the same story: everything is resident on one device.

## 7. Success Metrics

- **Continuity:** in a multi-turn session the assistant correctly uses facts stated in earlier turns without restatement.
- **Persistence:** a fact stated in one session (e.g. a budget ceiling) is semantically recalled in a later session via episodic memory.
- **Personalization:** with a profile set, the synthesis "action" paragraph references the buyer's situation; the same report with no profile is generic.
- **Privacy (binary, the one that matters):** during a full chat + report flow, zero outbound requests leave the device — verifiable by network inspection.
- **Reliability:** chat and report flows complete (in degraded form) even when the embedding server or RAG is down.

## 8. Future Work

- **Profile depth:** extend beyond `monthly_income` to structured savings, existing debt, FHSA/RRSP balances, and explicit risk tolerance — richer inputs to both the engine and synthesis.
- **Memory management:** surface, edit, and delete remembered episodic facts; add decay/recency weighting and de-duplication.
- **Report-aware chat:** let the assistant directly reference a specific saved report ("compare this to the Riverdale one I saved") by joining chat against `saved_reports`.
- **Report compare view:** side-by-side diff of two saved reports.
- **Streaming replies** for lower perceived chat latency.
- **Multi-user** (explicitly out of scope now) if the device is ever shared.
